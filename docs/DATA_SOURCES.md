# Where the data comes from, and how it is related

## The one-paragraph answer
No public dataset contains *tenant-level renewal outcomes after a specific intervention*. So the project uses
(1) **public data to make a synthetic PMS look realistic** (rent levels, unit sizes, maintenance-violation rates, ...) and
(2) a **synthetic longitudinal PMS** whose *true* intervention effects are known, so causal methods can be scored.
Real data validates realism; synthetic data supplies causal ground truth (your slide 14 principle).
Public data only ever touches the generator through `data/processed/calibration.json`.

## How everything is related (entity-relationship + feature flow)

```
 public data --calibrate.py--> calibration.json --+
                                                  v
 properties 1--* units 1--1 tenants 1--* leases      <- generated by synthetic_pms.py (hidden concern per tenant drives everything below)
                              |
                              +--* payments            (12 monthly rows: due, paid, days_late)
                              +--* service_requests    (created, resolved; open if resolved is NULL)
                              +--* communications      (sentiment, response_hours, message_text)
                              +--* satisfaction_surveys (not every tenant answers)
                              +--* interventions       (action taken, who assigned it, cost)   [history cohort + agent actions]
                              +--* renewal_outcomes    (renewed 0/1, source = historical | simulated_demo)
                              +--* audit_log           (recommendation / approval / execution / outcome events)

 all tables --features.py--> feature_store (one row per tenant, 23 features, computed AS OF the decision date: no leakage)
 oracle.csv.gz (NOT in the database): true P(renew) under every action, hidden concern, logging propensities.  Only evaluation code and
 the dashboard's "evaluator mode" read it.
```

Two cohorts live in the same tables (`tenants.cohort`):
* **history** (12,000 tenants): past decisions. Each has a logged action (chosen by "past managers" who reacted to risk signals -> *confounded*;
  15 % were randomised in a pilot) and an observed renewal outcome. Models are trained on this.
* **current** (3,000 tenants): lease ends in 30-90 days, no action taken yet. The agent recommends for these; they are also the evaluation cohort.

## Using REAL tenant data later
Replace step 2 by an ETL that fills the same tables from the property manager's export, and skip the oracle. Everything else (features, models,
agent, dashboard, diagnostics, off-policy evaluation) runs unchanged; only the ground-truth metrics disappear - which is exactly why
`04_evaluate.py` section 4-5 (overlap, balance, refutations, E-values, off-policy evaluation) only use logged data.
